# 评审验证报告：nsm_server 纸带不一致问题

针对评审提出的"同 DFA 多次执行不一致、准确率仅 38.5%、应接 verdict_head"三条主张，逐一实测验证。

## 验证方法

1. 读全部 13 个 `.tape` 文件逐条比对
2. Executor 同输入跑 3 次测确定性（含 logit 边界检查）
3. 三个示例 NL（T1 表格/T2 规则/T3 打乱句）分别解析比对 spec
4. 服务器端同输入连发 3 次端到端比对纸带
5. 补跑 demo 确切配置（k=4, L=8）的正式评测（n=200）

## 验证结果

### 评审主张 1：「同 DFA 同输入，38.5% 准确率」——数据错误 + 归因错误

- **数字错了**：13 条纸带中第 8 步 state=3（正确）的是 **8 条**，state=0 的是 5 条。
  即 **61.5% 正确**，不是 38.5%。
- **归因错了**：纸带不一致不是 Executor 抖动。

### 评审主张 2：「Executor 非确定性，state_head 边界被浮点翻转」——**证伪**

实测（正确 spec，连续 3 次前向）：

```
trial0: states=[1,1,0,1,1,1,0,3] last_logits=[-1.878,-1.984,-2.261, 9.825]
trial1: states=[1,1,0,1,1,1,0,3] last_logits=[-1.878,-1.984,-2.261, 9.825]
trial2: states=[1,1,0,1,1,1,0,3] last_logits=[-1.878,-1.984,-2.261, 9.825]
```

- 输出**逐位相同**（bit-identical）。
- 争议步的 logit 差距 **11.7**（9.825 vs -1.878）——根本不存在"边界"，浮点噪声不可能翻转。
- 服务器端到端同输入 3 次调用：纸带逐位一致，全部 ACCEPT。

### 评审主张 3：「应该接 verdict_head」——**建议本身有害**

`verdict_head` 在训练中**从未见过接受集信息**（`build_executor_batch` 只传转移表和输入串，
accepting 不在模型输入里）。它是个结构性哑头：对这个例子，即使执行完全正确，
verdict_head 输出 **REJECT（错）**，而现有的 state 判定输出 ACCEPT（对）。
**当前 state-based 判定是正确设计，评审的"修复"会把对的改错。**

### 不一致的真正来源

tapes 的 attn 序列全同（`0,3,2,0,3,3,2,1`）是因为第 8 步查询的转移结构 (q=0,sym=1) 不变；
变化的是**解析出的转移目标值**。实测：三个示例 NL 此刻解析全部正确（(A,1)->3）。
因此 5 条错带只能来自**当时输入侧的变异**（用户编辑过文本/不同的 NL 措辞 → 解析 spec 不同）。
**Executor 忠实地执行了它收到的 spec——错的 spec 给出错的结果，这不是执行器的 bug，是输入差异。**

### 评审主张 4：「训练/部署分布 gap」——部分成立，已闭合

k=4 与 L=8 确实未出现在 extended_eval 中。补测（dfa_executor_k32，n=200 新 DFA）：

| 配置 | acc | α_struct |
|---|---|---|
| k=4 L=8（demo 确切配置） | **1.000** | +0.745 |
| k=4 L=20 | 1.000 | +0.728 |
| k=4 L=50 | 1.000 | +0.720 |
| k=5 L=8 | 1.000 | +0.661 |
| k=2 L=20 | 1.000 | +0.730 |

**部署分布下依然 100%。**

## 真正值得做的改进（评审没点到的）

1. **纸带加头**：tape 文件头部写入解析出的 spec 摘要（k, accepting, delta hash）——
   让每个纸带可追溯"执行的是哪份 spec"，输入侧差异立即可见。
2. **解析回显 + 一致性自检**：服务返回中附 spec；同输入多跑时比对 spec hash，
   不同则提示"解析不一致"而非默默执行。
3. ~~接 verdict_head~~：不做（理由见上）。
